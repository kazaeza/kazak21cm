# Архитектура

## 1. Путь сообщения

```
ВК-чат (клиент)  ──► ВК-сборщик (браузер, ПК пользователя, пн-пт 9-19) ─┐
                                                                        ├─► АРХИВ ─► подготовка кодом ─► МОДЕЛЬ ─► проверка ─► ТАСКЕР ─► уведомления
Telegram «Дизайн» ─┐                                                    │
Telegram «Рабочий» ┴► Telegram-бот (сервер, круглосуточно) ─────────────┘
```

1. **Сборщики** приносят сообщения. ВК: раз в 3 минуты в рабочее окно, последние 50 перечитываются, чтобы поймать правки и удаления. Telegram: бот получает сообщения сразу.
2. **Архив** хранит сообщение как есть, со всеми версиями после правок. Из архива берутся все цитаты.
3. **Подготовка кодом (без ИИ):** реплаи (у сообщения есть номер того, на что ответили), автор и его сторона, время, рабочие часы, правки, удаления, чат-источник, склейка серий сообщений одного автора.
4. **Модель (Gemini Flash)** получает правила, участников с ролями, открытые задачи, последние ~40 сообщений из всех чатов и новые сообщения. Возвращает список операций в JSON (`schema/ops.schema.json`).
5. **Проверка кодом:** сообщение и задача существуют, переход статуса допустим, схема соблюдена. При нарушении проход повторяется один раз, потом сообщения уходят в «Разбор».
6. **Таскер** применяет операции. Уверенность ≥ 0.85: применяется. 0.70-0.85: применяется с пометкой «проверьте». Ниже 0.70: «Разбор».
7. **Уведомления** (Telegram, личные сообщения) только в рабочее окно.

## 2. Расписание

- Окно: пн-пт, 09:00-19:00 по московскому времени (`Europe/Moscow`). Все метки времени в архиве хранятся с offset `+03:00`. Праздники и переносы из `config/holidays.yaml`.
- ВК-сборщик и вызовы модели работают только в окне. Telegram-бот собирает круглосуточно, модель разбирает накопленное в окне, в 09:00 первым проходом.
- Курсор: номер последнего сохранённого сообщения по каждому чату. Ничего не теряется между окнами.
- Модель вызывается только при новых сообщениях. Если последнее сообщение моложе 60 секунд, проход откладывается на следующий тик (не более 2 раз): серия «Нужно… / И ещё… / Срочно!» обрабатывается целиком.
- Большие пачки (утро понедельника) режем на порции по ~100 сообщений.

### Время ответа считается в рабочих минутах

Считаем только пересечение интервала с пн-пт 9:00-19:00. Пример: план отправлен вт в 19:52, клиент ответил ср в 9:15. Это 15 минут, а не 13 часов. Реализация в прототипе: функция `workMin` в `prototype/protokol.html`. «Рабочий день» в подписях это 10 часов (`2 раб. д 6 ч`).

## 3. Формат сообщения в архиве

```jsonc
{
  "id": 1232,                      // сквозной номер в нашем архиве
  "source": "vk | tg_design | tg_work",
  "native_id": "…",                // номер сообщения в самой платформе
  "chat": "…",                     // peer_id в ВК или chat_id (+ thread_id) в Telegram
  "author": "<people.id>",
  "ts": "2026-11-11T19:48:00+03:00",
  "text": "…",
  "reply_to": 1230,                // сквозной номер или null
  "forwarded": [ ... ],            // вложенные пересланные сообщения
  "attachments": [ {"type": "photo|doc|voice|sticker|link", "name": "…", "url": "…", "transcript": "…"} ],
  "versions": [ {"ts": "…", "text": "…"} ],   // история правок, первая версия первой
  "deleted_at": null,
  "raw": { }                       // исходный ответ платформы, для разбора ошибок
}
```

Правка сообщения создаёт новую версию, а не новое сообщение. Агент должен видеть, что текст менялся и когда (в примере прототипа клиент дописала условие через 3 минуты после отправки).

## 4. Модель данных таскера

| Сущность | Поля |
|---|---|
| `tasks` | id (T-n), title, kind (`client`/`internal`), status, created_by, owner, executor, deadline_text, deadline_ts, summary, ball (`agency`/`client`, since, what) |
| `events` | task, message, type, interpretation, confidence, flag, created_by (`agent`/`human`) |
| `requirements` | task, key, versions[] {value, message, ts} |
| `promises` | person, what, due, task, message, audience (`client`/`internal`), result (`ok`/`late`/`none`/`partial`/`wait`) |
| `review_queue` | message, reason, candidates[] {task, p}, looks_like_idea |
| `agent_runs` | ts, message ids, модель, ops, токены, стоимость, ошибка схемы |
| `corrections` | message, что исправил человек. Идут в промпт как примеры |
| `people` | из `config/people.local.yaml` |

Типы событий: `created`, `accepted`, `question`, `answer`, `req_change`, `req_add`, `result`, `result_internal`, `revision`, `approved`, `internal_ok`, `tension`, `offchat`, `deleted`, `nudge`, `promise`, `agree`, `assign`, `progress`.

Статусы: `new` → `work` → `review` → `revisions` → `done`, а также `cancelled` и `paused`.

| Статус | Что его двигает |
|---|---|
| `new` | Клиент поставил задачу, от агентства ответа нет |
| `work` | Наш ответил «приняли», «берём», «сделаем» (реплаем или по смыслу) |
| `review` | Агентство прислало результат клиенту: файл, фото, текст, ссылку |
| `revisions` | Клиент вернул результат с замечаниями, каждое замечание идёт в ТЗ |
| `done` | Согласовал участник клиента: «ок», «согласовано». Одинокий 👍 даёт пониженную уверенность |
| `cancelled`/`paused` | Клиент отменил или отложил |

### Согласование

Единого «последнего слова» у клиента нет: решения принимают все его участники. SMM-специалист закрывает большинство финальных вопросов, но не все.

- Согласование любого участника клиента записывается с именем того, кто согласовал (`approved_by`). Пометки «вне роли» нет.
- `done` не окончательный. Если после согласования другой участник клиента просит правки («поправьте вот это»), задача возвращается в `revisions` с флагом `reopened_after_approval`. Новые замечания идут в ТЗ.
- Мяч снова у агентства. На экране задачи помечается, кому показать исправление: тому, кто вернул задачу. После нового результата показываем его ему, а не только тому, кто закрывал первым.
- Само возвращение не конфликт и не противоречие: `flag_contradiction` ставим только если новое указание расходится с прошлым ТЗ.

Результат, показанный внутри команды («Дизайн»), в `review` не переводит: клиенту его ещё не отправили. Это событие `result_internal`.

## 5. Что отслеживает агент

- **Принятие:** кто из наших ответил, когда и что пообещал.
- **ТЗ и версии:** по каждому требованию «было → стало, кто и когда».
- **Противоречия:** новое указание расходится со старым, или двое от клиента говорят разное.
- **Чей ход:** у кого мяч и сколько рабочего времени он там лежит.
- **Обещания и сроки** обеих сторон, отдельно внутренние и данные клиенту.
- **Цепочка между чатами:** поручение клиента в ВК, передача исполнителю в Telegram, результат, отправка клиенту.
- **Расхождения между чатами:** внутри что-то обещали или сделали, а клиенту в ВК не сказали.
- **Уход из чата:** личка, созвоны. Фиксируется как `offchat`, плюс ручная заметка.

## 6. Правила для модели (основа системного промпта)

1. Ты ничего не цитируешь. Ссылайся на сообщения номерами из архива.
2. Своё толкование пиши в `interpretation`, коротко, с оговоркой при неуверенности.
3. Реплай (`reply_to`) это жёсткая связь, он важнее догадок.
4. Несколько сообщений подряд от одного автора это одна мысль.
5. Правка сообщения это новая версия того же сообщения.
6. Болтовня, приветствия, стикеры без смысла: `mark_noise`. Не создавай задачи из шума.
7. Идея без срока и формата («может, сделаем розыгрыш, подумайте») не задача: `needs_review` с `looks_like_idea`.
8. Одинокое «ок» или 👍 без реплая: низкая уверенность.
9. При конфликте указаний фиксируй противоречие через `flag_contradiction`. Сам победителя не выбирай.
10. Согласует любой участник клиента, записывай, кто именно (`approved_by`). Если после согласования другой участник клиента просит правки, верни задачу в `revisions` с флагом `reopened_after_approval` и запомни, кому показать исправление.
11. Обещание внутри команды не равно обещанию клиенту: поле `audience`.
12. Голосовые приходят с расшифровкой, при плохой расшифровке понижай уверенность.
13. Не уверен: `needs_review` с кандидатами и вероятностями.

## 7. Модель и стоимость

- Gemini Flash через Google API, платный тариф. На бесплатном Google может использовать запросы для улучшения своих продуктов, а в них переписка клиента и внутренние чаты.
- Структурированный вывод по схеме. Поддержка схемы у Gemini это подмножество JSON Schema: `schema/ops.schema.json` придётся проверить и при необходимости упростить (плоский объект с nullable-полями вместо `anyOf`).
- Flash слабее топовых моделей на тонких вещах: ирония, «ок» без реплая, противоречия. Поэтому всё, что можно сделать без ИИ, делает код, неуверенное идёт в «Разбор», а точность проверяется на истории до запуска.
- Возможная вторая ступень: спорные случаи (уверенность ниже 0.85, изменение ТЗ, противоречие) перепроверяет более сильная модель Gemini. Решаем по тесту.
- Голосовые: расшифровка ВК или аудио в Gemini. Скриншоты читает как картинки.
- Оценка стоимости (ориентир по ценам Flash-моделей на ноябрь 2026, проверить по актуальному прайсу): до 50-80 проходов в день по ~14 тыс. токенов на вход и ~3 тыс. на выход, около $15-30 в месяц на три чата. Сервер добавит несколько долларов.
- Gemini API доступен не из всех стран. Если он недоступен с компьютера пользователя, вызов модели делает сервер в поддерживаемом регионе.

## 8. Стек (предложение)

Python, Playwright (ВК-сборщик), aiogram (Telegram-бот), SQLite на старте и PostgreSQL потом, FastAPI и простой веб-интерфейс по прототипу, Telegram-бот для уведомлений в личку.

## 9. Тест до запуска

1. Берём историю ВК и экспорт Telegram за один период.
2. Вручную размечаем 100-200 сообщений (к какой задаче, какое событие, что изменилось в ТЗ, есть ли противоречие). Пользователь правит разметку.
3. Прогоняем Flash, считаем точность по привязке к задаче, статусу и изменению ТЗ. Отдельно смотрим связи между чатами.
4. Если точность не устраивает: правим правила и примеры, пробуем вторую ступень. Без этого в боевой режим не идём.

## 10. Риски

| Риск | Что делаем |
|---|---|
| Слетела сессия ВК (капча, код, выход на всех устройствах) | Сборщик останавливается, обходить проверку не пытается, пишет пользователю в Telegram. Таскер показывает «данные устарели с…» |
| Блокировка личного аккаунта | Только чтение, один чат раз в 3 минуты, только рабочие часы, обычный компьютер пользователя. Риск полностью не убрать. Запасной вариант: отдельный аккаунт-наблюдатель |
| Модель ошиблась | Код делает всё, что можно без ИИ. Неуверенное в «Разбор». Откат любой операции. Тест на истории |
| Общение вне чата | Личка и созвоны не видны. Ручные заметки, напоминание после «созвонились» |
| Приватность | Переписка клиента и внутренние чаты уходят в Google. Платный тариф, проверить договор с клиентом, предупредить команду |
| Лишнее в рабочем чате | Модель помечает не относящееся к проекту, в таскере оно не появляется. Сами сообщения при этом уходят в Google. Если неприемлемо: отдельный чат или темы |
| Бот Telegram простоял больше суток | Telegram не вернёт пропущенное. Бот должен жить на сервере 24/7 |
