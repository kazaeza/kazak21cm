# Большой файл в облачной сессии: как завезти, где держать, как обработать

## Что умеет облачная сессия (замер 2026-11-19)

- **Ресурсы:** 16 ГБ памяти, 4 ядра, около 30 ГБ свободного диска. Файл на 1 ГБ открывается и
  ужимается без проблем.
- **Сеть.** Исходящий HTTPS идёт через прокси. Окружение «Default» открыто для любых хостов, а у
  окружения для конкретного репозитория список хостов может быть свой: проверь `get_environment`.
  Прокси перешифровывает TLS, поэтому клиентам нужен `/root/.ccr/ca-bundle.crt` (для FigCraft это
  `FIGCRAFT_CA_FILE`).
- **Входящих соединений нет.** До контейнера никто не достучится. Значит, сервер для человека
  поднимать здесь бессмысленно: только для локальных тестов на 127.0.0.1.
- **До компьютера человека облачная сессия не дотягивается.** «Add folder» есть только в
  локальных сессиях. Remote Control может быть не подключён: проверь `list_computer_folders`.
  Папки из Remote Control (у пользователя была `figCraft` на Windows-ПК) могут числиться в
  `cannot_be_used` с причиной `not_available`: тогда её нельзя подключить, пока приложение на
  ПК не обновят (2026-11-20 было именно так). Если станет доступна, `request_computer_folder`
  снимает вопрос переноса: файлы остаются на ПК.

## Каналы: как файл попадает в облако и обратно

| Канал | Размер | Статус | Заметки |
|---|---|---|---|
| Свой `figcraft-server` | до ~700 МиБ `.figcraft` | **проверено** (локально) | Человек публикует из приложения, ты входишь и делаешь `save_file`: файл у тебя. Обратно — правки идут вживую. Ещё это и хранилище, и совместная работа |
| Публичный `collab.craftapps.dev` | до 8 МиБ | **проверено** (`serverInfo`) | Только маленькие файлы. Удаление через 30 дней, без шифрования на сервере |
| Хранилище с API (Dropbox, Яндекс Диск, S3) | любой | **канал проверен, обмен с хранилищем человека нет** | Скачивание 1 ГиБ через прокси прошло целиком за 54 с (~20 МБ/с, 2026-11-20); `cloud-api.yandex.net`, `www.dropbox.com`, `drive.google.com` достижимы. Ключ — через `request_credential`, прокси подставит его сам. Обратно — новый файл, исходник не перезаписывать |
| Публичная ссылка на скачивание | любой | не проверено | `curl -L`. Любой со ссылкой скачает файл: не для конфиденциального |
| Вложение в чат («Add files») | неизвестно | не проверено | Гигабайт вряд ли пройдёт |
| GitHub | до 100 МБ на файл | ограничение GitHub | Для больших `.figcraft` не годится |
| MCP-коннекторы (Google Drive и т.п.) | — | не годится | Содержимое шло бы через контекст модели |
| Локальная сессия на ПК человека | любой | — | Файл никуда не едет: Claude Code на его компьютере |

## Порядок для файла больше 700 МиБ

1. **Узнай, из чего он** (`file-format.md`, «Из чего состоит размер»), для чего макет (экран или
   печать) и нужна ли живая работа.
2. **Один раз завези файл** через хранилище с API или работай в локальной сессии.
3. **Ужми:** `shrink_figcraft.py`, с `--max-side` 2048 для экрана и ~3600 для печати A4.
   Покажи «до и после» (`render`), исходник не трогай.
4. **Дальше на выбор:**
   - **живьём** — человек публикует ужатый файл на свой сервер, работа идёт по разделу A
     `SKILL.md`;
   - **файл туда-обратно** — правишь напрямую (ниже) и отдаёшь новую версию через хранилище.

## Работа с файлом напрямую (проверено на 961 МиБ, FigCraft 0.18.1)

- Открыть, поправить текст и сохранить заняло 7,5 с и 3,5 ГБ памяти на пике. Попытка публикации
  того же файла доходила до 5,8 ГБ.
- Пакет правок идёт одним процессом `figcraft_live.py`: `open_file`, команды, `save_file` с новым
  путём. Шаги `join` и `sync` не нужны.
- Показывай человеку картинки кадров (`figcraft-cli export --node`), а не гоняй гигабайт ради
  просмотра.

```json
[
  {"tool": "open_file", "args": {"path": "/abs/work/menu.figcraft"}, "timeout": 900},
  {"tool": "inspect_document", "args": {"depth": 2, "outline": true}},
  {"command": "edit.findReplace", "params": {"find": "Капучино 250", "replace": "Капучино 270"}},
  {"tool": "save_file", "args": {"path": "/abs/work/menu-edited.figcraft"}, "timeout": 900}
]
```

## Где держать рабочие файлы

- **Временные** (скачанное, ужатое, экспорты) держи в scratchpad сессии. Он чистится при
  перезапуске, так что всё нужное сразу отдавай человеку.
- **Не коммить `.figcraft` больше нескольких МБ** в git. Маленькие результаты (сторис, превью)
  коммитить можно.
- **Ссылки, коды, токены и ключи** не пиши ни в файлы репозитория, ни в логи.

## Публичная ссылка Яндекс Диска (проверено 2026-11-20 на файле 2,45 МБ)

1. `GET https://cloud-api.yandex.net/v1/disk/public/resources?public_key=<ссылка>` даёт имя, размер,
   `md5` и `sha256`: сверь с ними скачанное.
2. `GET .../v1/disk/public/resources/download?public_key=<ссылка>` даёт `href` (хост
   `downloader.disk.yandex.ru`). Токен не нужен.
3. `curl -L -o файл "$href"`. Параметры передавай через `curl -G --data-urlencode`.

Скачивание 2,45 МБ заняло 2 с, всё вместе с запросами к API 4 с, `md5` и `sha256` совпали.
Открыть, поправить текстовый слой (`text.set {id, characters}`), сохранить новым именем: 0,3 с.
Итог открывается заново, изменился ровно один слой, исходник не тронут (sha256 до и после).

**Запись обратно на Яндекс Диск не проверена.** Нужен OAuth-токен, а API Диска ждёт
`Authorization: OAuth <токен>`. Форма `request_credential` умеет префиксы Bearer, Token, Key и т.п., а
`OAuth` в списке нет, так что неясно, примет ли Диск `Bearer`. Пользователь отказался от записи на Диск,
поэтому результат вернули без хранилища (см. «Как отдать результат человеку»).

## Как отдать результат человеку

| Способ | Размер | Заметки |
|---|---|---|
| `SendUserFile` | проверено на 2,4 МБ и на 386 МиБ (инструмент сообщил о доставке; получение человеком отдельно не подтверждено) | Файл должен лежать в рабочей папке или scratchpad. Человек получает карточку со скачиванием. Самый простой путь для небольших файлов |
| Коммит в репозиторий | до 100 МБ на файл | **Только если репозиторий приватный.** Проверь `list_repos` (поле `visibility`): рабочие файлы человека нельзя класть в публичный репозиторий |
| Хранилище с API | любой | Нужен ключ с правом записи |
| Свой сервер FigCraft | до ~700 МиБ | Человек сам заходит в файл и сохраняет его себе |

Scratchpad живёт только до конца сессии: всё, что человеку нужно, отдавай до её конца.

## Замеры на файле 386 МиБ (2026-11-20, публичная ссылка Яндекс Диска, FigCraft 0.18.1)

Файл: 384 картинки (385 МиБ), `document.json` 5,5 МиБ, 5524 слоя, 681 верхнеуровневый объект, 1779 текстовых слоёв.

| Шаг | Время | Пик памяти |
|---|---|---|
| Скачивание 404 439 485 байт (API → `href` → `curl -L`), `md5` и `sha256` совпали | 41 с (~10 МБ/с) | — |
| `figcraft-cli info` | 1,5 с | 645 МиБ |
| `open_file` + `inspect_document` по всем 1779 текстам (`allPages`, `depth` 1000, `maxBytes` 8 000 000) | 1,5 с | 998 МиБ |
| `open_file` + `text.set` + `save_file` новым именем | 36,5 с | 1,9 ГиБ |
| `shrink_figcraft.py --max-side 2048` | 136 с | 2,1 ГиБ |
| 4 экспорта кадров 1080×1350 и 1080×1920 | 3,4 с | — |

- Повторное открытие правки: из 1779 текстов изменился один, лишних и пропавших нет, исходник не тронут.
- Ужатие: 385,7 → 125,5 МиБ (−67 %), заменено 617 слоёв из 630, 13 оставлены как были. Кадры того же
  размера, средняя разница с оригиналом 1,4–3,4 из 255 (на глаз не отличить).
- `save_file` занимает почти всё время правки: сам `text.set` мгновенный.
