# Передача контекста

Написано 17.11.2026 в конце первой сессии. Она шла в облаке и не имела доступа к браузеру пользователя. Продолжение идёт в локальной сессии на компьютере пользователя, где есть браузер с залогиненным ВК.

Порядок чтения: этот файл, `ARCHITECTURE.md`, `COLLECTORS.md`, `../config/settings.yaml`, потом прототип `../prototype/protokol.standalone.html`.

Настоящие имена людей и их роли здесь не записаны: репозиторий публичный. Они лежат в промпте, которым пользователь запустил сессию, и в `config/people.local.yaml` (файл в `.gitignore`).

## 1. Задача

Пользователь работает в SMM-агентстве и ведёт соцсети клиента. С клиентом общаются в беседе ВК. Беседа шумная: много сообщений, задач, уточнений, правок. В общении с клиентом бывают конфликты, поэтому нужны точные цитаты: кто что написал и что имел в виду.

Нужен агент, который каждые несколько минут читает чаты и ведёт таскер:

- клиент написал новое поручение: агент создаёт задачу;
- наш сотрудник ответил: задача помечается «принято» с комментарием;
- кто-то ответил реплаем на это сообщение: это тоже записывается в задачу;
- везде сохраняются цитата, автор, время и пометка «как понял агент», отдельно от цитаты.

Слова пользователя: «Нужны прям цитаты, кто что написал, и что имел ввиду. Потому что у нас есть проблемки с общением с этим клиентом.»

## 2. Источники

| Чат | Платформа | Как читаем | Кто в нём |
|---|---|---|---|
| Беседа с клиентом | ВК | Браузер с сессией пользователя, пн-пт 9:00-19:00, раз в 3 минуты | клиент и агентство |
| «Дизайн» | Telegram | Бот, круглосуточно | только наши, состав уточнить |
| «Рабочий» | Telegram | Бот, круглосуточно | только наши, возможно с другими проектами, уточнить |

## 3. Участники (на уровне ролей)

Клиент, 3 человека: SMM-специалист (ставит основную часть задач), дизайнер (участвует в принятии решений, в том числе вне дизайна), руководитель (в работу почти не вмешивается, часто бывает на созвонах).

Агентство, 5 человек: ведущий проекта, новый аккаунт-менеджер, руководитель агентства (в работу не вмешивается), сотрудник, пользователь (владелец проекта таскера).

Что это значит для агента:

- Согласование нужно привязывать к человеку и его роли. Согласие дизайнера клиента вне дизайна записывается как «согласовала <имя> (вне роли)» и само задачу в «Готово» не переводит.
- Сообщения руководителя клиента выделяются и сразу уходят уведомлением.
- Созвоны агент не видит. На фразы «созвонились», «на звонке решили» он просит оставить заметку, а договорённость помечает «без письменного подтверждения».
- Определять, что чей-то текст написала нейросеть, не нужно: точность низкая, а ярлык на живом человеке рискован. Надёжно ловятся противоречия с прошлыми словами и новые требования.

Формат списка: `config/people.example.yaml`.

## 4. Решения

| Решение | Кто принял | Статус |
|---|---|---|

| Использовать личный аккаунт пользователя | пользователь | решено. Риск блокировки и капч объяснён, ответа про отдельный аккаунт-наблюдатель не было |
| Пометка «прочитано» в ВК допустима | пользователь | решено |

| Обработка: Gemini Flash, ключ Google API даст пользователь | пользователь | решено |
| Таскер свой, отдельный. Прототип подходит | пользователь | решено |
| Два чата Telegram читает бот | пользователь | решено |
| Историю ВК за последний месяц собирает ассистент через браузер | пользователь | решено, ждёт локальной сессии |
| Историю Telegram берём из экспорта Telegram Desktop (JSON) | ассистент | предложено |

| ВК-сборщик остаётся на компьютере пользователя | ассистент | предложено, ответа нет |
| Внутренние задачи из Telegram как отдельный тип | ассистент | предложено, ответа нет |
| Расхождения между чатами показываем сигналами | ассистент | предложено, прототип показывает |

Принципы, которые закреплены в дизайне:

1. Цитаты берутся из архива слово в слово. Модель возвращает только номера сообщений.
2. Толкование модели («как понял») показывается отдельно от цитаты.
3. Уверенность ниже 0.70: сообщение уходит в «Разбор», решает человек.
4. Любую операцию агента можно откатить. Ручные исправления становятся примерами для модели.
5. Сроки ответов считаются только в рабочее время пн-пт 9-19.
6. Агент только читает. В чатах он ничего не пишет и не ставит реакции.

## 6. Что заблокировало первую сессию

Нужен доступ к браузеру с сессией ВК. К облачной сессии не удалось подключить компьютер пользователя (список папок был пуст). Пользователь решил создать новую сессию локально.

## 7. План ближайшей сессии

1. Проверить окружение: Python 3.11+, установленный Chrome. Создать `tasker/collector/` и виртуальное окружение.
2. Пилот ВК по `COLLECTORS.md`: профиль браузера, пользователь входит сам, записываем сетевые ответы, выясняем, отдаёт ли ВК JSON или придётся читать разметку.
3. Короткий отчёт `docs/vk-probe-findings.md` без текстов переписки: что нашли, какой способ выбираем.
4. Выгрузка истории беседы за последние 30 дней в `data/vk_history.jsonl` (формат в `ARCHITECTURE.md`, в git не попадает).
5. Проверка качества выгрузки вместе с пользователем: реплаи, правки, вложения, голосовые, пересылки, порядок сообщений.
6. Дальше: размеченный набор 100-200 сообщений, тест Gemini Flash (ключ у пользователя, хранить в `.env`), затем таскер, сервер и Telegram-бот.

## 8. Открытые вопросы к пользователю

1. Часовой пояс и страна, откуда работает компьютер.
2. Кто на стороне клиента принимает окончательные решения? Может ли SMM-специалист клиента согласовывать сам?
3. Кому слать уведомления «клиент ждёт ответа»? Предположение: ведущему проекта и аккаунт-менеджеру, руководителю агентства только недельная сводка.
4. Что за люди в дизайнерском чате? Только свои или есть внешние? В рабочем чате только этот проект или и другие?
5. Нужны ли внутренние задачи, которых не было в чате клиента?
6. Готов ли пользователь арендовать маленький сервер (несколько долларов в месяц)? Регион выбираем так, чтобы Gemini API отвечал оттуда.
7. Отвечает ли Gemini API с компьютера и из региона сервера? Включён ли платный тариф?
8. Какую беседу ВК читаем (название или ссылка) и сколько дней истории нужно, по умолчанию 30?
9. Предупредит ли пользователь команду, что в Telegram-чатах будет бот?

## 9. Правила работы

- Репозиторий публичный: данные чатов, профили браузера, токены и настоящие имена не коммитим (см. `CLAUDE.md`).
- В ВК только читаем. Не печатаем в поле сообщения, не ставим реакции, не нажимаем «отправить».
- Вход в ВК делает пользователь в открытом окне браузера. Логин, пароль и коды мы не видим и не храним.
- Капча, запрос кода или подтверждения: останавливаемся и сообщаем пользователю, обходить не пытаемся.
- Токены «как у официальных приложений ВК» не получаем и не используем. Они дают доступ ко всему аккаунту и нарушают правила ВК.
- Историю прокручиваем медленно: не чаще одной подгрузки в 2-3 секунды.
- Перед коммитом: `git status`, `git diff --cached --stat`, убедиться, что в индексе нет `data/`, `private/`, профилей и ключей.
- Ветка разработки: `ccr-27af123f-srnxas`. Pull request не создаём, пока пользователь не попросит.
